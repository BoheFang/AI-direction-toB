§ 01

一、项目定位:我们在做一个什么样的产品

一句话:面向公司销售材料生产全链路的 Agent 工作台——从"人推"改为"Agent 推 + 人决策"。

销售材料的生产今天散落在 GTM、产线、销售、售前四类角色手里,靠 IM 群、周会、Excel 台账推着走——派发靠人催、写作靠 Word 满天飞、审核靠肉眼、归档靠人搬。GTM Copilot 的定位就是把这条链路收进一个系统:Agent 顶掉重复劳动,人只做决策和创作。

§ 04

四、下一阶段规划(按优先级四步走)

前三步都在为第四步"解决方案生成"做铺垫,四步严格先后依赖。

01
材料生成体验打磨
主链路虽通,但前端呈现仍有细节需优化——重点是执行过程五阶段流式可视化与任务名称自动生成。
  • 五阶段流式呈现:任务解析 → 材料检索 → 内容起草 → 格式化 → 交付 · 每阶段实时状态可见
  • 任务名称自动生成:根据 prompt 首帧解析出简短标题,避免"未命名任务"堆积
  • 失败态与人工介入:每一步失败都能被前端捕获、可重试、可手动接管
  • 生成 Skill 持续优化:基于产线试用反馈迭代 Prompt、工具调用与生成质量,形成评测—优化—回归闭环
M2
02
材料生成 1→10 改进场景
从"从零生成"扩展到"基于已有材料迭代改进",覆盖修订对话与本地往返两条改稿路径,把 0→1 升级为全生命周期材料运营。
  • 修订对话:在系统内针对某段落 / 图 / 数据直接下达修改指令,Agent 定点改写
  • 本地往返:导出 docx → 客户改 → 传回系统 → Agent 识别 diff → 合并入主稿
  • 版本树:一份材料的所有分支 / 定制版 / 客户返稿都挂在同一份主稿下
M2
03
产品材料库维护与上新
解决方案生成的数据 / 知识底座。现状:只有首页前端,详情页尚未落地——需补齐各产线 24 类标准材料 内容。
  • 详情页落地:每类材料有清晰的字段 schema、状态、责任人、更新记录
  • 24 类内容补齐:白皮书 / 案例 / FAQ / 竞品分析 / 报价…每类由对应产线负责
  • 治理机制:过期提醒、抽检、下架流程,防止材料库变成"档案坟"
M3
04
解决方案生成场景(发布主打能力)
用户选行业 → 勾多个产线材料库(seaf + AI 知识库 + Qpass…)→ 生成定制化方案。技术难点:多库检索融合、跨产线语义对齐、Agent 编排 / RAG / 多轮规划。产品从"单点工具"升级为"解决方案引擎"。
  • 多库检索融合:seaf / AI 知识库 / Qpass 三个异构底座的统一检索接口
  • 跨产线语义对齐:不同产线术语 / 卖点 / 参数体系的对齐层
  • Agent 编排 · RAG · 多轮规划:从行业 brief 到成品方案文档的端到端 pipeline

§ 06

六、当前最大的不确定性(风险)

项目继续推进面临以下不确定性——M4 是唯一发布节点,任何一个失控都直接影响发布质量。

风险 1 技术选型与开发效率缺少资深判断,有一定试错成本 阻塞 M4
问题
缺少资深工程师做前置判断,只能靠试错收敛方向。
影响
M4 的解决方案生成技术选型复杂度更高,同样靠试错收敛。
风险 2 多材料库编排的技术路径未验证 阻塞 M4
问题
第四步是新命题——走 RAG?Agent-as-Tool?Sub-Agent 编排? 三种方案在多库融合场景下各有短板,没有专人预研。
影响
方向选错,M4 会推倒重来;而 M4 是唯一发布节点——直接决定发布能不能如期。
风险 3 Agent 输出效果的评测体系缺失 全阶段
问题
0-1 项目没真实用户反馈,判断 Agent 输出好坏完全靠主观拍脑袋——没有基准集、没有评分维度、没有回归 pipeline。
影响
迭代方向不可信;发布前无法系统验证质量,发布后无法数据驱动优化——每次改动都是"感觉变好了"。
